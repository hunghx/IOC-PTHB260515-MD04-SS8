2. Bộ 5 Vũ Khí Của Resilience4j
Annotation Ý nghĩa nghiệp vụ
@CircuitBreaker Đóng/ngắt mạch tự động khi phát hiện service phụ lỗi
@Retry Thử lại khi gặp lỗi tạm thời (mạng chập chờn, 503)
@RateLimiter Khống chế số lượng request tối đa trong khoảng thời gian
@TimeLimiter Chặn request chạy quá lâu (ngăn cạn kiệt thread)
@Bulkhead Phân vùng thread pool riêng cho từng dịch vụ gọi ngoài
Lesson 2 • Cài đặt circuit breaker + fallback
3. Cơ Chế Hoạt Động Của Circuit Breaker (3 Trạng Thái)
⚙️ Cấu hình Circuit Breaker trong application.yml
resilience4j.circuitbreaker.instances:
  paymentService:
    sliding-window-type: COUNT_BASED
    sliding-window-size: 10              # Xét trong 10 request gần nhất
    failure-rate-threshold: 50           # Lỗi >= 50% là ngắt mạch (OPEN)
    wait-duration-in-open-state: 10s     # Chờ 10s trước khi sang HALF_OPEN
    permitted-number-of-calls-in-half-open-state: 3
💡 Giải thích các tham số then chốt
Tham số Ý nghĩa thực tế
sliding-window-size Số lượng request thu thập để tính toán tỷ lệ lỗi
failure-rate-threshold Ngưỡng % lỗi kích hoạt trạng thái OPEN
wait-duration-in-open-state Thời gian cách ly để service phụ tự hồi phục
permitted-calls-in-half-open Số lượng request cho qua để thử nghiệm
Lesson 2 • Cài đặt circuit breaker + fallback
4. Cài Đặt @CircuitBreaker & Xây Dựng Phương Thức Fallback
Code Service với @CircuitBreaker và Fallback
@Service
public class OrderService {

    @Autowired
    private PaymentClient paymentClient;

    @CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
    public String processPayment(OrderRequest request) {
        return paymentClient.callPaymentApi(request);
    }

    // Phương thức Fallback dự phòng khi mạch OPEN hoặc gọi bị lỗi
    public String paymentFallback(OrderRequest request, Throwable ex) {
        return "Cổng thanh toán đang bảo trì. Đơn hàng chuyển sang: Chờ thanh toán COD!";
    }
}
⚠️ 3 Quy Tắc Bắt Buộc Khi Viết Hàm Fallback
Quy tắc Mô tả chi tiết
1. Cùng kiểu trả về Kiểu dữ liệu trả về của hàm fallback phải giống hệt hàm gốc (VD: String)
2. Cùng danh sách tham số Phải nhận đầy đủ các tham số của hàm gốc theo đúng thứ tự
3. Thêm tham số Throwable Tham số cuối cùng bắt buộc là Throwable ex hoặc Exception cụ thể để bắt lỗi
4. Vị trí nằm cùng Class Nằm trong cùng class Spring Bean để cơ chế AOP ủy quyền chính xác
Lesson 3 • Cấu hình Retry, giới hạn tần suất, timeout
5. Cấu Hình Cơ Chế Tự Động Thử Lại Thông Minh (@Retry)
Cấu hình Retry trong application.yml
resilience4j.retry.instances:
  paymentService:
    max-attempts: 3                     # Số lần thử tối đa
    wait-duration: 2s                   # Thời gian chờ giữa các lần
    retry-exceptions:                   # Chỉ thử lại khi gặp lỗi tạm thời
      - java.io.IOException
      - org.springframework.web.client.HttpServerErrorException
    ignore-exceptions:                  # Không retry lỗi nghiệp vụ client
      - com.example.InvalidPaymentException
Gắn Annotation @Retry vào Code
@Service
public class PaymentGatewayService {

    @Retry(name = "paymentService", fallbackMethod = "retryFallback")
    public PaymentResponse pay(PaymentRequest req) {
        return restTemplate.postForObject("/pay", req, PaymentResponse.class);
    }

    public PaymentResponse retryFallback(PaymentRequest req, Throwable ex) {
        return new PaymentResponse("FAILED", "Thanh toán lỗi sau 3 lần thử");
    }
}

6. Giới Hạn Tần Suất (@RateLimiter) & Chặn Timeout (@TimeLimiter)
1. Giới hạn tần suất gọi với @RateLimiter
# Cho phép tối đa 5 request trong chu kỳ 10 giây
resilience4j.ratelimiter.instances:
  orderApiRateLimit:
    limit-for-period: 5
    limit-refresh-period: 10s
    timeout-duration: 0ms # Quá tải là từ chối ngay (429)
@RateLimiter(name = "orderApiRateLimit", fallbackMethod = "rateLimitFallback")
public String createOrder() { return "Order Created"; }

public String rateLimitFallback(Throwable ex) {
    return "Hệ thống đang quá tải, vui lòng thử lại sau vài giây!";
}
2. Ngắt kết nối chạy quá lâu với @TimeLimiter
# Bắt buộc kết thúc trong 3 giây
resilience4j.timelimiter.instances:
  inventoryCheck:
    timeout-duration: 3s
    cancel-running-future: true
// @TimeLimiter thường áp dụng cho CompletableFuture / Reactor
@TimeLimiter(name = "inventoryCheck", fallbackMethod = "timeFallback")
public CompletableFuture<Boolean> checkInventory() {
    return CompletableFuture.supplyAsync(() -> slowInventoryApi());
}

public CompletableFuture<Boolean> timeFallback(Throwable ex) {
    return CompletableFuture.completedFuture(false);
}
Lesson 4 • Xử lý lỗi khi service phụ bị lỗi
7. Các Chiến Lược Xử Lý Lỗi Nghiệp Vụ (Fallback Patterns)
Chiến lược 1: Trả về Cache Cũ (Stale Cache)
// Khi Product Catalog Service lỗi, đọc dữ liệu cũ từ Redis
@CircuitBreaker(name = "catalogService", fallbackMethod = "getCachedProducts")
public List<Product> getPopularProducts() {
    return catalogClient.fetchPopular();
}

public List<Product> getCachedProducts(Throwable ex) {
    return redisTemplate.opsForList().range("cached_popular", 0, -1);
}
Chiến lược 2: Graceful Degradation (Giảm cấp dịch vụ)
// Khi Recommendation AI bị sập, hiển thị sản phẩm ngẫu nhiên mặc định
@CircuitBreaker(name = "recommendService", fallbackMethod = "getDefaultRecommend")
public List<String> getPersonalizedRecommend(Long userId) {
    return aiClient.getPredictions(userId);
}

public List<String> getDefaultRecommend(Long userId, Throwable ex) {
    return List.of("Áo thun cơ bản", "Bình giữ nhiệt");
}
Chiến lược 3: Hàng đợi dự phòng (Message Queue / Asynchronous)
// Khi Notification Service lỗi, gửi Message vào Kafka/RabbitMQ để gửi sau
public void notifyFallback(OrderEvent event, Throwable ex) {
    kafkaTemplate.send("failed_notifications_topic", event);
}
Chiến lược 4: Chuyển hướng phương thức tương đương (Failover)
// Khi Cổng thanh toán VNPay lỗi, tự động chuyển sang Cổng Momo
public PaymentResult payFallback(PaymentDto dto, Throwable ex) {
    return momoClient.pay(dto);
}

8. Giám Sát Sức Khỏe & Trạng Thái Mạch Qua Spring Boot Actuator
1. Mở Endpoint Giám Sát trong application.yml
management:
  endpoints:
    web:
      exposure:
        include: health, info, metrics, circuitbreakers, circuitbreakerevents
  endpoint:
    health:
      show-details: always
  health:
    circuitbreakers:
      enabled: true
